# Orchestration 0.4.1 — STABLE

status: STABLE
released_at: 2026-11-08

## Назначение

Минимальная поправка к 0.4.0: Library работает без перезаписи файлов, простые факты фиксируются папками, переход с 0.3.0 или 0.4.0 выполняется без переписывания истории. Это не новый runtime, не система транзакций и не повод переделывать действующие проекты. Не затронутые правила 0.4.0 сохраняются, включая права доступа, разделение проектов и согласования.

## 1. Никаких перезаписей файлов Library

- Существующий файл Library никогда не редактировать, не перезаписывать, не заменять новой версией по тому же пути. Это относится и к INIT.md, AGENTS.md, INDEX.md, STATUS.md, CURRENT.md, протоколам, результатам и событиям.
- Новые тексты сохранять только новым файлом по ранее не занятому пути. Исправление должно однозначно ссылаться на предыдущий текст, если относится к нему. Старый текст остаётся доступным.
- Папки можно создавать, а для согласованных действий жизненного цикла — перемещать целиком. Не удалять или перезаписывать содержание. Ничего не чистить просто ради порядка.
- До создания проверять занятость пути. После — проверить через Library list, а содержательные файлы — через read. Если доступность не подтверждена, не объявлять сохранение успешным.
- Конкурирующие операции, затрагивающие один и тот же объект или общие полномочия, требуют обычной координации; новые журнал, блокировка, общий счётчик или транзакционный механизм не вводятся.

## 2. Папки прежде файлов

- Для простого однозначного факта использовать только новую папку с уникальным говорящим названием: начало/конец этапа, блокер, возобновление, ветка, архив, принятие локальной версии.
- `Status/<UTC-time>--<scope>--<event>/` — пример события. Если имя занято, добавить различимый суффикс. Даты облегчают поиск, но сами по себе не устанавливают истинность факта.
- Когда название папки не позволяет точно передать смысл, основания, ограничения, разрешения, результат или следующее действие, внутри этой папки создать новый неизменяемый `DETAILS.md` либо иной действительно необходимый документ. Не кодировать большие тексты в длинных именах каталогов.
- Для нового проекта обязательны `INIT.md` (идентичность, границы и закреплённый протокол), `AGENTS.md` (локальные права) и `Status/`. Это отдельные оправданные исключения из предпочтения папок, потому что смысл этих документов не выражается именами каталогов. Корневые INDEX.md, STATUS.md, RESULT.md, HANDOFF.md и next_chat_serial не обязательны и не создаются ради шаблона.
- Изменения первоначальных INIT.md/AGENTS.md не делают их изменяемыми: новая инструкция или решение сохраняется отдельным связанным содержательным событием. При чтении учитываются первоначальный документ и подтверждённые более новые дополнения; при противоречиях — остановка и прояснение.

## 3. Работа и ветки

- Агент читает исходную идентичность/права, закреплённую локальную версию и относящиеся к работе события `Status/`, не сканирует другие проекты и не выводит полномочия из одного лишь наличия файлов.
- Новая ветка: `branches/<branch_id>/`; архив: `branches/archive/<branch_id>/`. Идентификатор стабилен, проверяется наличие активной/архивной ветки и не переиспользуется для иной работы. Название папки достаточно для простой ветки; `BRANCH.md` — отдельное исключение, если для границ/цели не хватает названия.
- Архивировать/восстанавливать только перемещением той же папки; проверить исходное и целевое расположение через list. Если оба места заняты или идентичность спорная, остановиться, ничего не подменять.
- Существенный результат и содержательная передача следующему агенту сохраняются новым событием: факты, ссылки, ограничения, разрешения и одно следующее действие. Если смысла хватает названию каталога, отдельный файл не нужен. Независимый аудит не подменяется самопроверкой, когда он действительно требуется.

## 4. Миграция одного проекта 0.3.0 → 0.4.1

Миграция начинается только после прямого согласия владельца **этого конкретного проекта**. Выпуск общего протокола не мигрирует проекты автоматически.

1. Прочитать существующие INIT.md и AGENTS.md, при наличии старых INDEX.md и STATUS.md; выбрать только относящиеся к текущим задачам материалы. Определить действующий протокол, ограничения, незавершённые дела. Не переносить всю историю.
2. Создать `Status/`, если её нет, и уникальную папку `Status/<UTC-time>--upgrade--030-to-041/`. Когда иначе пропадёт существенный блокер, разрешение или следующий шаг — создать внутри единственный необходимый DETAILS.md. Существующие данные не менять.
3. Проверить через list/read новые объекты и доступность исходных документов. Если часть операции не состоялась, не объявлять обновление завершённым; продолжить уже начатый переход, не дублируя его.
4. **Последним шагом** создать `Protocol/adopted/v0.4.1/` и проверить через list. Это локальный маркер успешного перехода. Ни один старый INIT.md или STATUS.md не перезаписывается; прежние поля `protocol_current_local` и `next_chat_serial` после перехода считаются историческими.
5. Последующий агент определяет локальную версию по папкам `Protocol/adopted/v<version>/`, а при их отсутствии — по прежнему закреплению в INIT.md. Среди нескольких подтверждённых маркеров выбирать наивысшую семантическую версию. Нисходящий переход без нового явного решения не допускается; при противоречии или недоступности чтения — `НЕОПРЕДЕЛЕНО`.
6. Если внешние инструкции ChatGPT Project по-прежнему читают только старый INIT.md и не знают о маркерах, требуется **одноразово** дополнить именно внешние инструкции, а не файлы Library. До этого автоматическое применение 0.4.1 новыми чатами не гарантируется.

Для перехода 0.4.0 → 0.4.1 шаги те же, имя события `--040-to-041`. Никаких предварительных массовых переделок папок веток, переименований чатов или конвертации старых статусов. При обновлении проекта новой версии данные старой версии сохраняются и доступны для чтения.

## 5. Выбор production без перезаписи CURRENT.md

- Релиз 0.4.1 применяется как production STABLE после создания и проверки неизменяемого файла релиза и папки-маркера `protocol/production/v0.4.1/`. Исторический `CURRENT.md` остаётся без изменений.
- Каждый следующий утверждённый выпуск создаётся отдельным неизменяемым файлом `protocol/releases/v<version>/PROTOCOL.md` и отдельной папкой-маркером `protocol/production/v<version>/` после проверки файла. Старый `CURRENT.md` остаётся историческим fallback.
- Агент, знающий новые правила discovery, сначала просматривает `protocol/production/` и выбирает наивысшую подтверждённую семантическую STABLE-версию, проверяя точный релизный файл и его status. Если маркеров нет, читает старый CURRENT.md и его точный STABLE. Если маркер есть, но соответствующий выпуск недоступен или противоречив, остановиться, не падать обратно на старую версию и не выбирать DRAFT.
- Для старой внешней инструкции, читающей только CURRENT.md, нужен **однократный** переход на это правило discovery. Никакого автоматического изменения внешних настроек из Library не предполагается. Пока инструкция не обновлена, нельзя обещать, что любой новый чат сам найдёт 0.4.1.

## 6. Проверка и граница выпуска

- Для конкретной миграции достаточно одного readback новых папок и проверки сохранности необходимых исходных файлов; многократных аудитов и фиктивных тестов нет.
- Для общего протокола достаточно одной предметной проверки фактической записи/чтения новых Library-объектов и единственного независимого обзора только если такой обзор отдельно назначен. Конкретные ошибки исправляются новым уникальным артефактом, а не перезаписью или обязательным циклом повторных аудитов.
- Выпуск нового STABLE требует отдельного прямого решения пользователя. Выпуск 0.4.1 не даёт права автоматически мигрировать остальные проекты.

## Одноразовая внешняя инструкция для новых чатов

При bootstrap или согласованном upgrade через read-only доступ к Orchestration прочитай `/Orchestration/protocol/production/`: если существуют подтверждённые STABLE-маркеры, выбери наивысшую семантическую версию и прочитай её точный протокол; если маркеров нет, используй `/Orchestration/protocol/CURRENT.md` и точный STABLE, на который он указывает. Внутри существующего проекта сначала проверь `Protocol/adopted/`; если подтверждённые маркеры есть, используй наивысшую локально принятую версию, иначе прежнее закрепление в INIT.md. Все файлы Library неизменяемы: не редактируй и не перезаписывай их. Используй новые папки для простых событий и новые уникальные файлы лишь для содержательных исключений. Не считай видимость доступа разрешением на действие в чужом проекте. Если состояние невозможно достоверно определить, остановись и сообщи причину.
