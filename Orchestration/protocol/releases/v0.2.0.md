# Project Bootstrap Protocol 0.2.0

version: 0.2.0
status: STABLE
released_at: 2026-10-27
supersedes: 0.1.0
compatibility: backward-compatible extension of 0.1.0
migration_required: no for projects already managed by 0.1.0; PRE_ORCHESTRATION legacy adoption requires 0.2.0+ semantics

## 1. Trigger

Treat natural-language intent to create/start/init a project as `PROJECT_BOOTSTRAP`. Do not require an exact magic phrase.

`PROJECT_CREATE`, where present in older material, is an alias for the new-project subflow of `PROJECT_BOOTSTRAP`.

## 2. Bootstrap / upgrade discovery and bootloader contract

A brand-new target project and an unpinned existing project must not depend on target-project Orchestration files for protocol discovery.

A bootstrap-capable environment therefore provides one external discovery hook, installed at the host/user/workspace orchestration layer, with this semantic contract:

```text
On natural-language intent either (a) to create/initialize a project or (b) to upgrade/adopt Orchestration for an existing project, read /Orchestration/protocol/CURRENT.md plus only the exact Orchestration sources referenced by the applicable production pointer. This is read-only cross-project authorization for Orchestration discovery only; it does not authorize reading any other project.
```

Required sequence for new-project bootstrap:

1. Detect `PROJECT_BOOTSTRAP` intent.
2. Read `/Orchestration/protocol/CURRENT.md` through the discovery hook.
3. Read the exact release file referenced by the production STABLE pointer.
4. In production mode, require a non-empty production STABLE pointer and verify the referenced release is `STABLE`.
5. Before target-project writes, establish persistent create/update/readback capability. Prefer capability introspection; if unavailable, a reversible project-local write/read/delete probe is allowed.
6. After seed creation, read back every seed file and required metadata before claiming initialization succeeded.

Required sequence for existing-project upgrade/adoption discovery:

1. Detect semantic existing-project upgrade/adoption intent, including ordinary-language requests equivalent to `PROJECT_UPGRADE`.
2. If trustworthy local Orchestration metadata already pins a protocol, use the managed-project upgrade contract in section 14.1.
3. If the existing project is unpinned or lacks trustworthy Orchestration metadata, read `/Orchestration/protocol/CURRENT.md` through the same discovery hook and read only the exact production STABLE upgrade/adoption source(s) it references.
4. Production legacy adoption must use the production STABLE pointer. A DRAFT candidate may be exercised only in an explicitly development/test flow and is never a production fallback.
5. Until section 14.3 authorizes bounded `LEGACY_ADOPTION_PREFLIGHT` control-plane writes, discovery remains Orchestration-only and read-only.

The hook authorizes read-only discovery from Orchestration only. It does not authorize any other project, device, account, credential, browser state or remembered context.

Defined blockers:

- `BOOTSTRAP_BLOCKED_DISCOVERY_UNAVAILABLE`
- `BOOTSTRAP_BLOCKED_PROTOCOL_POINTER`
- `BOOTSTRAP_BLOCKED_NO_STABLE_PROTOCOL`
- `BOOTSTRAP_BLOCKED_STORAGE_UNAVAILABLE`
- `BOOTSTRAP_BLOCKED_PERSISTENCE_VERIFICATION`
- `BOOTSTRAP_EXISTING_PROJECT`
- `UPGRADE_BLOCKED_DISCOVERY_UNAVAILABLE`
- `UPGRADE_BLOCKED_PROTOCOL_POINTER`
- `UPGRADE_BLOCKED_NO_STABLE_PROTOCOL`

On any blocker, stop the affected path, state the exact blocker and do not claim success or improvise a protocol from memory, another project, or a DRAFT candidate.

## 3. Bootstrap response contract

On bootstrap:

1. Run the discovery/bootloader contract.
2. State the exact protocol candidate/release being used and whether the run is development/test or production.
3. Determine whether the target project is new or already exists.
4. If it exists, do not overwrite it; route to resume/repair/upgrade.
5. For a new project, give the Conductor the short Project Instructions snippet.
6. Do not stop merely because the snippet was shown; require user action only if that UI setting is genuinely needed before safe continuation.
7. Run persistent-storage preflight.
8. Create the minimum project seed: `INIT.md`, `INDEX.md`, `STATUS.md`, `AGENTS.md`.
9. Persist required metadata and read it back.
10. If no actionable goal is known, ask one compact intent question.
11. Normalize the answer into goal, expected outcome, scope, constraints, unknowns, gates and completion criteria.
12. Select the minimum role chain required by risk/uncertainty.
13. Persist current stage/gate/next step.
14. Continue or hand off using the lifecycle and serial-allocation contracts.

## 4. Conductor prompt

Default missing-intent prompt:

```text
Опишите, что нужно сделать и какой результат ожидаете. Если есть сроки, ограничения, запреты или обязательные условия — добавьте их.
```

Ask additional questions only when they block a correct/safe next step.

## 5. Required project metadata

```text
project_name
project_code
created_at
protocol_created_with
protocol_current_local
update_policy
current_stage
current_gate
next_chat_serial
```

Default update policy: `EXPLICIT_MIGRATION`.

The bootstrap chat consumes serial `01`; a newly initialized project therefore persists `next_chat_serial: 02`.

## 6. Persistent context

Project files are authoritative persistent state. Chat history and model memory are not authoritative when project files exist.

Do not recursively scan unrelated Library content. Read root entry points, then only current task/branch materials referenced by them.

Bootstrap is not successful until the seed and required metadata pass persistent readback.

## 7. Context isolation

The existence or visibility of an external device, account, credential, connection, browser state, local path or remembered system does not establish project membership or authorization.

Use external sources only when current project scope/instructions establish relevance and permission.

The bootloader exception is narrow read-only access to the Orchestration bootstrap source defined in section 2. It is not general cross-project permission.

## 8. Source priority / conflict resolution

Within project scope, apply this order:

1. Current explicit Conductor/user instruction for intent, scope and authorization.
2. Project-specific mandatory safety/legal/business constraints and explicit local protocol overrides.
3. Verified current state of the target system/resource.
4. Current project task/audit/result/handoff for the active branch.
5. Project `STATUS.md`.
6. Project `INIT.md`, `INDEX.md` and local `AGENTS.md`.
7. The project's pinned global protocol release.
8. Chat history, model memory or inferred recollection.

A lower-priority source must not silently override a higher-priority one. User instruction governs desired action/permission, not contradictory factual observations; preserve intent and verified state separately when they differ. If item 1 conflicts with a project-specific mandatory safety/legal constraint in item 2, execution is blocked by that hard constraint. A mutable business rule/local override may be changed only when the current instruction explicitly changes it; persist the new rule before relying on it. Mandatory platform/system safety constraints remain outside and above this contract.

## 9. Local AGENTS.md

Local `AGENTS.md` is project-specific. It contains only:

- project roles and authority boundaries;
- project constraints/prohibitions;
- project resource/access rules;
- project approval ownership;
- explicit local protocol overrides/deltas with scope/rationale;
- a pointer to `protocol_current_local` / the pinned global release.

Do not copy universal bootstrap, lifecycle, serial, source-priority, handoff or upgrade rules into every project. Record only project-specific deltas.

## 10. Roles and independent audit

- `Conductor` — human intent/approval interface.
- `Bootstrap Coordinator` — first-chat initializer/resumer.
- `Strategist` — route/design.
- `Auditor` — independent verification and verdict.
- `Coordinator` — workflow progression/orchestration.
- `Executor` — bounded implementation.
- `Researcher` — scoped fact discovery.

Roles may be combined for low-risk work only when an independent gate is not required.

For every explicitly independent audit gate:

1. The auditor must run in a separate chat/agent context from the author/executor whose work is being audited.
2. The auditor must not mutate the audited implementation while issuing its verdict.
3. Required fixes return to the owning author/editor/executor.
4. Re-audit occurs only after fixes are persisted.
5. A `fresh independent re-audit` uses a new audit chat/agent context that did not perform the fixes being judged.

## 11. Lifecycle and handoff

Every substantive agent result must define:

```text
AGENT_DECISION: CONTINUE | ARCHIVE_READY
NEXT_STEP: <one concrete action>
NEW_AGENT_REQUIRED: YES | NO
```

If `NEW_AGENT_REQUIRED: YES`, the handoff must contain:

- exact next role;
- exact `CHAT_TITLE` using a serial already reserved under section 13;
- mandatory project paths to read;
- current gate/run-state/result;
- confirmed facts that must not be re-asked/re-proved without new contradictory evidence;
- permissions/approvals already granted, with scope and limits;
- completed/closed gates and work that must not be repeated;
- active blockers/open gates;
- prohibitions and stop-gates;
- expected artifacts/result paths;
- completion criterion;
- requirement to apply this lifecycle contract to the next agent's result.

A replacement chat must be able to continue from persistent files and the handoff without reading prior chat history.

## 12. Anti-stall rule

`pending`, `waiting`, processing, sync, upload, indexing and read-back are not terminal states by themselves.

If continuation can happen without user participation, keep an active owner/trigger or route to a new agent with that trigger. Use a user gate only when user action/decision is genuinely required.

## 13. Chat naming and next_chat_serial

Default title:

`<PROJECT_CODE>-<NN> · <Branch> · <Role/Task>`

`next_chat_serial` is the next unused project-wide serial.

Allocation rules:

1. Bootstrap chat = `01`; persisted next value after bootstrap allocation = `02`.
2. Before allocating another chat, read authoritative `next_chat_serial = N` immediately before reservation.
3. Reserve `N` for the new chat and persist `next_chat_serial = N + 1` before emitting the handoff/title.
4. Read back the increment before publishing `CHAT_TITLE`.
5. Reserved/abandoned/archived/replaced/deleted numbers are never reused.
6. Retry, replacement and re-audit chats consume the next unused project-wide number.
7. Allocation is a project-level critical section. Parallel branches must serialize allocation through the authoritative coordinator/state writer; if conflict-safe writes are unavailable, branches do not allocate independently.
8. Use at least two digits through `99`; continue naturally at `100+`.

## 14. PROJECT_UPGRADE and legacy adoption contract

Existing Orchestration-managed projects pin their local protocol release. A newer global release must not silently modify them.

### 14.1 Managed-project upgrade

For a project that already has trustworthy Orchestration metadata including `protocol_current_local` and authoritative `next_chat_serial`, default `EXPLICIT_MIGRATION` remains:

1. Read current project state, local overrides and pinned release.
2. Read global CURRENT and target release.
3. Compare/classify read-only; no migration write to operational project state.
4. Produce a concrete migration plan: target version, affected files, exact intended changes, preserved facts/gates/approvals, validation and rollback/recovery.
5. If nontrivial/breaking or authority/gate semantics change, independently audit that exact plan before any migration mutation authorization. This pre-approval audit gate is satisfied only by `AUDIT_PASS` on that exact plan; `AUDIT_PASS_WITH_FIXES` or `AUDIT_FAIL` returns the plan to its owner for correction and a new independent re-audit.
6. Obtain explicit Conductor approval for the exact audited migration plan and target version. Approval is plan-specific.
7. If the approved plan changes materially, obtain new approval; if the changed plan is nontrivial/breaking, re-audit it first.
8. Only after all required audit and Conductor-approval gates are satisfied may migration writes to operational project state occur.
9. Update protocol metadata and project changelog/handoff.
10. Read back changes and verify completed work, confirmed facts, permissions and active domain gates were not reset/reopened.

A user approval given before a required independent audit does not authorize migration writes until the exact audited plan reaches the approval/apply gate.

### 14.2 PRE_ORCHESTRATION legacy classification and entry

Semantic `PROJECT_UPGRADE` / Orchestration-adoption intent for an existing project is a discovery trigger under section 2 even when the project has no local Orchestration metadata.

If an existing project predates Orchestration and lacks trustworthy pinned protocol metadata and/or authoritative `next_chat_serial`, classify it as `PRE_ORCHESTRATION_LEGACY`. Do not invent prior Orchestration state and do not treat old chat names, task numbers or branch numbers as project-wide serials unless an authoritative project artifact explicitly defines them that way.

For production adoption, load the production STABLE release through the section 2 discovery hook. If that discovery path is unavailable, stop with `UPGRADE_BLOCKED_DISCOVERY_UNAVAILABLE`; do not infer adoption rules from memory or another project. A DRAFT release is development/test-only.

A legacy project enters `LEGACY_ADOPTION_PREFLIGHT` before normal migration.

### 14.3 LEGACY_ADOPTION_PREFLIGHT control plane

The purpose of preflight is to make the exact migration plan independently auditable without mutating the legacy project's operational state.

Before `AUDIT_PASS` and post-audit Conductor approval, the only target-project writes allowed are bounded control-plane artifacts under:

`/<PROJECT>/orchestration-adoption/`

Allowed pre-approval writes are limited to:

- `STATE.md` — authoritative adoption history: `adoption_run_id`, run state, target protocol, adoption project code, plan identity, audit/approval gate and authoritative adoption serial state; it also contains the fixed readback/validation record for control-plane writes;
- `PLAN.md` — the exact migration plan submitted for audit;
- `HANDOFF-*.md` — handoffs required to route the adoption audit/re-audit;
- `AUDIT-*.md` — independent audit verdict artifacts bound to an exact plan identity and target version.

These writes are an explicit exception to the normal pre-approval no-migration-write rule. They authorize orchestration of the migration process only. They must not:

- create or rewrite the target project's operational `INIT.md`, `INDEX.md`, `STATUS.md`, `AGENTS.md`, `CHANGELOG.md` or task/branch state as if adoption had succeeded;
- change business/domain facts, completed work, existing gates or permissions;
- touch external systems, infrastructure, credentials or production state;
- claim that the project is migrated or pinned to the target protocol.

### 14.4 Legacy adoption STATE, project code and serial continuity

`orchestration-adoption/STATE.md` is authoritative control-plane history once a valid STATE has been created. Its serial state survives `FAILED`, `CANCELLED`, retry and replacement runs and is never reset or reused.

Before the first serial allocation, persist `adoption_project_code`:

1. If a trustworthy existing project code is present in authoritative project material, use it.
2. Otherwise derive the control-plane-only code deterministically as `ADP-<H8>`, where `<H8>` is the first eight uppercase hexadecimal characters of SHA-256 over the canonical target project root path string.
3. The derived adoption code is immutable for that adoption history and is used only for adoption chat titles/control-plane provenance.
4. `PLAN.md` must state the final operational `project_code`. If it differs from `adoption_project_code`, that difference is part of the exact audited/approved plan.

If no authoritative Orchestration serial state has ever existed, `LEGACY_ADOPTION_PREFLIGHT` establishes a new namespace:

1. Existing pre-Orchestration chats do not retroactively consume Orchestration serials.
2. Persist `next_chat_serial: 01` in `STATE.md` together with `adoption_project_code` before allocation.
3. To allocate the independent adoption auditor, immediately apply section 13: reserve `01`, persist `next_chat_serial: 02`, read it back, then publish `<ADOPTION_PROJECT_CODE>-01 · Adoption · Auditor`.
4. Every retry, replacement and re-audit consumes the next serial under section 13.
5. After successful adoption, carry the authoritative current `next_chat_serial` from adoption STATE into the project's normal persistent protocol metadata.
6. If a trustworthy existing Orchestration serial state is discovered, use it instead of creating a new namespace.

Every adoption run persists an `adoption_run_id` and one explicit run state. The minimum normative state set is:

`PREFLIGHT`, `AUDIT_PENDING`, `FIXES_REQUIRED`, `AUDIT_PASS`, `AWAITING_CONDUCTOR_APPROVAL`, `APPLYING`, `COMPLETED`, `FAILED`, `CANCELLED`.

A later attempt after `FAILED` or `CANCELLED` must either resume the same `adoption_run_id` when recovery is valid, or create a new `adoption_run_id`; in both cases it carries forward the same authoritative monotonic `next_chat_serial` and retains prior plan/audit history. It must never reinitialize serial state.

If a previously valid adoption STATE is missing, unreadable, corrupt, or internally inconsistent, do not silently create a new STATE or serial namespace. Stop with `ADOPTION_BLOCKED_STATE_UNAVAILABLE` or `ADOPTION_BLOCKED_STATE_INCONSISTENT` as applicable. Recovery must reconstruct/repair authoritative control-plane history from verifiable persisted artifacts before any new serial allocation. If no valid adoption STATE has ever existed, first initialization is allowed as defined above.

Pre-Orchestration labels that visually resemble `<PROJECT_CODE>-NN` remain non-authoritative. When such a collision is detected, adoption titles keep their reserved Orchestration serial and add an operator-visible `Adoption` branch label rather than renumbering or reusing serials.

This control-plane STATE does not itself make the project Orchestration-managed.

### 14.5 Exact PLAN identity, audit and approval

Before audit handoff, the submitted plan receives an immutable audit-target identity persisted in `STATE.md`:

```text
plan_revision: <monotonic integer within adoption history>
plan_digest_sha256: <SHA-256 of the exact persisted PLAN.md bytes>
plan_target_protocol: <exact target version>
```

The plan-identity rules are normative:

1. Write `PLAN.md`, read it back successfully, compute/verify its SHA-256 digest, and only then persist the matching identity in `STATE.md`.
2. `STATE.md` readback/validation metadata must record the artifact path, observed digest, validation timestamp/result, and the matching `plan_revision`.
3. Every `AUDIT-*.md` verdict must identify `plan_revision`, `plan_digest_sha256`, and `plan_target_protocol`; a verdict without all three does not satisfy the audit gate.
4. `AUDIT_PASS` applies only to that exact identity.
5. Post-audit Conductor approval must identify the same `plan_revision`, `plan_digest_sha256`, and target protocol version. Approval given before the audit or for a different identity does not satisfy the apply gate.
6. Any content change to `PLAN.md` after the identity was established increments `plan_revision`, produces a new digest, invalidates every prior `AUDIT_PASS` and approval for application, and requires a fresh independent audit before a new post-audit approval can authorize writes.

The adoption sequence is:

1. Inspect the legacy project read-only and classify `PRE_ORCHESTRATION_LEGACY`.
2. Build the exact migration plan in memory.
3. Create/update only the bounded adoption control plane, persist/read back `PLAN.md`, establish the exact plan identity above, and set run state `AUDIT_PENDING`.
4. Reserve a serial and hand that exact persisted plan identity to a separate independent auditor.
5. The auditor may write only its audit artifact and bounded adoption run-state; it must not implement the migration it is judging.
6. `AUDIT_PASS_WITH_FIXES` or `AUDIT_FAIL` sets/retains `FIXES_REQUIRED` and returns the plan to its owner. A corrected plan gets a new revision/digest and requires a fresh independent re-audit.
7. `AUDIT_PASS` records the exact passed identity and advances to `AWAITING_CONDUCTOR_APPROVAL`.
8. Obtain explicit Conductor approval naming the same plan identity and exact target STABLE version. Approval given before the audit does not satisfy this post-audit gate.
9. Only then may run state advance to `APPLYING` and the approved operational migration writes occur.
10. Read back the migrated state, verify preserved facts/work/gates/permissions, set the project's normal protocol metadata to the successfully adopted STABLE target, carry forward serial state, and mark `COMPLETED`.
11. Retain or archive the adoption control-plane artifacts as provenance.

If adoption is cancelled or fails, set `CANCELLED` or `FAILED`; the legacy project remains legacy. The existing STATE, plan identities, audit artifacts and serial history remain authoritative provenance and must not be treated as successful migration state.

### 14.6 Applicability

Projects already correctly managed under `0.1.0` are not required to migrate merely because this legacy-adoption capability exists. They continue using their pinned release until an explicit `PROJECT_UPGRADE`.

## 15. Release policy

- DRAFT — development candidate; not default for production projects.
- STABLE — eligible for the production CURRENT pointer.
- DEPRECATED — retained for history/migration, not used for new projects.

`CURRENT.md` must expose separate development-candidate and production-STABLE fields.

While status is DRAFT, use `draft_created_at` / `draft_updated_at`. Reserve `released_at` for actual release promotion.

After promotion, historical release files are immutable; changes create a new version. A DRAFT candidate may be revised before promotion.
