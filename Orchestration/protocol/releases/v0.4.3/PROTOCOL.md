# Orchestration 0.4.3 — STABLE

version: 0.4.3
status: STABLE
released_at: 2026-11-08
baseline: /Orchestration/protocol/releases/v0.4.2/PROTOCOL.md

## Назначение

Уточнение PROJECT_UPGRADE: при переходе проекта с любой поддерживаемой закреплённой версии на другую версию обязательно формируется готовая к вставке в настройки ChatGPT Project **универсальная проектная инструкция**, которая не содержит номера закреплённой версии и не требует замены при следующих обновлениях протокола. Данное правило относится к процессу обновления, проводимому по 0.4.3, в том числе когда пользователь прямо запрашивает конкретную старую целевую версию (например, 0.3.0 → 0.4.2). Оно не переписывает историю уже завершённых миграций.

Правила 0.4.2 о границах доступа и явном разрешении миграции, неизменяемости файлов, допустимом отдельном удалении, предпочтении папок, маркерах локальной версии и простой миграции остаются в силе.

## 1. Результат каждого PROJECT_UPGRADE

При запросе «обнови проект с X до Y», «перейди на Y», «обнови до текущего STABLE» и аналогичном:

1. Определить **проект-адресат** и фактическую локально принятую версию по `Protocol/adopted/`, при отсутствии маркера — по прежним подтверждённым файлам проекта. Уточнить точную целевую STABLE-версию из запроса; при запросе «до актуальной» использовать `/Orchestration/protocol/CURRENT.md` и указанный там точный STABLE. Сам факт выпуска глобального релиза не является согласием на миграцию чужого проекта.
2. Выполнить краткую предметную миграцию выбранного проекта по правилам целевой версии: сохранить историю, не переписывать существующие файлы; достаточны необходимые события в `Status/`, разрешённые файлы-исключения и один подтверждённый маркер `Protocol/adopted/vY/` в конце. Не создавать ненужные планы, аудит-цепочки и тестовые проекты. Если целевая версия не поддерживает соответствующий способ миграции или данные противоречивы, не объявлять её завершённой.
3. **Независимо от того, нужно ли менять текст настроек**, сформировать после миграции готовую универсальную проектную инструкцию с фактическим корнем проекта. Показать её в чате полностью, одним копируемым блоком. Сохранить тот же текст отдельным новым файлом `PROJECT_INSTRUCTIONS.md` в уникальной папке события миграции `Status/<unique>--upgrade-to-Y/` как содержательное исключение. Проверить сохранённый файл чтением. Если миграция не завершена, всё равно можно выдать **предлагаемую** инструкцию, но явно обозначить её как не применённую и не создавать ложный маркер принятия версии.
4. Отдельно сообщить: (а) подтверждено ли принятие локальной версии в Library, (б) сформирован ли текст проектных инструкций и сохранён ли он, (в) были ли настройки ChatGPT Project фактически изменены. Если нет специального поддерживаемого инструмента для изменения настроек проекта, нельзя утверждать, что инструкция автоматически применена: пользователь вставляет её один раз вручную.
5. В дальнейшем при обновлениях этого же проекта **не заменять проектную инструкцию только потому, что изменилась версия Orchestration**. Новый агент определяет принятую версию из Library. Новую инструкцию при очередной миграции всё равно выдавать как обязательный результат, но при неизменном контракте она дословно совпадает с уже установленной и вставлять её повторно не нужно.

Инициирование PROJECT_UPGRADE не даёт права автоматически изменять настройки другого проекта или мигрировать соседние проекты.

## 2. Универсальный контракт проектной инструкции

Инструкция имеет только один проектно-специфичный параметр: `PROJECT_ROOT` — проверенный корень Library целевого проекта (например, `/agent-browser`). Она **не** содержит закреплённой версии, обязательного перечня старых файлов, номера чата или пути к фиксированному релизу. Текст шаблона сохраняется в `/Orchestration/protocol/releases/v0.4.3/PROJECT_INSTRUCTIONS_TEMPLATE.md`; при генерации заменить ровно `PROJECT_ROOT` на реальный путь. При отсутствии подтверждённого корня не придумывать путь и не объявлять инструкцию готовой.

Постоянный порядок на старте каждого чата:

- Сначала обнаружить `PROJECT_ROOT/Protocol/adopted/`; если есть подтверждённые локальные маркеры, определить последнюю принятую совместимую STABLE-версию. Если маркеров нет, прочитать `PROJECT_ROOT/INIT.md` и определить прежнее закрепление. Конфликт или недоступность не разрешать догадками.
- Через разрешённое **только для чтения** обнаружение `/Orchestration/protocol/` найти **точный исторический STABLE-релиз для локальной версии**. Для актуальных обновлений читать `/Orchestration/protocol/CURRENT.md` и релиз по ссылке. Формат расположения релиза может различаться; не предполагать, что локальная версия автоматически совпадает с глобальным production.
- Читать начальные проектные документы, локальные дополнения и относящиеся к задаче события/ветки. Старые INDEX.md/STATUS.md при необходимости читать как исторический контекст. Не считать исторические поля текущим состоянием при наличии более нового подтверждённого маркера.
- Соблюдать полномочия и изоляцию проекта, не перезаписывать файлы Library; удалять отдельными операциями только в пределах разрешения. Предпочитать папки для простых событий, новые файлы — для содержательных исключений. При передаче фиксировать существенные факты и одно следующее действие.
- Новую глобальную версию не внедрять автоматически: локальное обновление только по явному запросу и с проверкой реального результата. При запросе PROJECT_UPGRADE всегда выдавать универсальную инструкцию как результат, даже если она совпадает с текущей.

## 3. Совместимость и границы

- Инструкция из старого проекта с фиксированной строкой «Orchestration 0.3.0» заменяется **один раз после согласованной миграции** на универсальный вариант. Следующие миграции изменяют только Library и не требуют перенастраивать ChatGPT Project, пока сохраняется этот контракт.
- Новый чат со **старой** инструкцией может продолжать использовать старый протокол. Пока новый текст не вставлен в настройки, не обещать автоматического использования мигрированной версии.
- Для запроса перехода в конкретную версию `Y` не подменять `Y` текущей глобальной STABLE. Изменение глобального `CURRENT.md` не является миграцией любого существующего проекта.
- Не вводить независимый обязательный аудит, многократные тесты или дополнительный общий указатель только ради генерации текста инструкции. Один реальный readback созданных объектов достаточен.

## 4. Production

После явного указания реализовать версию 0.4.3 новый неизменяемый STABLE-релиз фиксируется по отдельному пути. Публикация production следует схеме 0.4.2: старый `CURRENT.md` удалить отдельным разрешённым действием, затем создать новый файл (никогда не `overwrite`) и проверить его чтением; для совместимости зарегистрировать `protocol/production/v0.4.3/`. Действующие проекты остаются закреплены за своими локальными версиями до отдельного PROJECT_UPGRADE.
